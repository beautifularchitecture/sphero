# Business Rules — u2-telemetry

Grounded in unit-of-work [unit-of-work], unit-of-work-story-map [unit-of-work-story-map], stories [stories], requirements [requirements], components [components], contract-summary [contract-summary], and functional-design questions [functional-design-questions].

## Source of Truth

```yaml
rules:
  - id: BR1.4.1
    statement: >
      U2 shall receive raw telemetry from the Sphero Mini over Bluetooth LE
      and normalize it into a RobotState entity with direction, orientation,
      color, position, and timestamp.
    category: validation
    applies_to: RobotTelemetry
    trigger: Raw BLE telemetry event received from Sphero Mini
    logic: >
      IF raw telemetry is received via Bluetooth LE THEN parse the telemetry
      into RobotState fields; IF any field is missing or invalid, fill it
      with a dash/null placeholder and still emit the RobotState event (lenient
      normalization per Q3); otherwise normalize all fields and emit.
    violation_behaviour: >
      Publish a RobotState event with placeholder values for missing fields;
      do not block on incomplete telemetry.
    source: [US1.4, AC1.4.1, FR1.1, NFR3]
  - id: BR1.4.2
    statement: >
      U2 shall publish a RobotStateChanged event on every robot state change
      for consumption by U3 StatsDisplay.
    category: policy
    applies_to: RobotTelemetry
    trigger: RobotState normalized and ready to publish
    logic: >
      IF RobotState is produced THEN publish an event on topic robot.state.changed
      with the full RobotState payload per Contract 2 (AsyncAPI).
    violation_behaviour: >
      If event delivery fails, fire-and-forget (no retry); the next event
      overwrites the previous one.
    source: [US1.4, AC1.4.1, NFR3, Contract-2]
  - id: BR1.4.3
    statement: >
      U2 shall handle telemetry connection errors and disconnections by
      reporting the error through U1 for chat UI display and robot stop,
      per US1.5 AC1.5.4.
    category: constraint
    applies_to: RobotTelemetry
    trigger: Bluetooth LE telemetry connection error or disconnection detected
    logic: >
      IF BLE connection drops or telemetry reception fails THEN U2 signals the
      error to U1 (which owns the chat UI and robot stop per FR4); U1 displays
      the error in the chat UI and stops the robot.
    violation_behaviour: >
      Error is surfaced in the chat UI by U1; robot does not continue moving
      on a lost telemetry connection.
    source: [US1.5, AC1.5.4, FR4, Q5]
  - id: BR1.4.4
    statement: >
      U2 shall receive and report command execution status from U1 per
      Contract 1 (sync callback).
    category: policy
    applies_to: RobotTelemetry
    trigger: U1 invokes the CommandExecutionStatus sync callback
    logic: >
      IF U1 calls the CommandExecutionStatus callback with {commandId, status, timestamp}
      THEN record the status and correlate it with the corresponding RobotCommand.
    violation_behaviour: >
      If the callback is unavailable, U1 logs and continues; telemetry proceeds
      without status correlation (per Contract 1 error handling).
    source: [Contract-1, US1.4]
  - id: BR1.4.5
    statement: >
      U2 shall use a backend-generated timestamp for each RobotState reading
      (per Q7).
    category: constraint
    applies_to: RobotTelemetry
    trigger: RobotState entity created from normalized telemetry
    logic: >
      IF a RobotState is created THEN set its timestamp field to the current
      ISO-8601 time generated by the backend, not a robot-provided timestamp.
    violation_behaviour: >
      RobotState readings carry backend-generated timestamps; robot-provided
      timestamps are not used.
    source: [Q7]
```

## Rules Summary

| Rule ID | Category | Applies To | Trigger | Statement (abridged) |
|---------|----------|------------|---------|----------------------|
| BR1.4.1 | validation | RobotTelemetry | Raw BLE telemetry received | Normalize telemetry into RobotState with lenient handling of missing fields |
| BR1.4.2 | policy | RobotTelemetry | RobotState ready to publish | Publish RobotStateChanged event on robot.state.changed topic |
| BR1.4.3 | constraint | RobotTelemetry | BLE connection error/disconnect | Stop robot, report error to chat UI via U1 |
| BR1.4.4 | policy | RobotTelemetry | U1 sync callback fires | Receive and report CommandExecutionStatus from U1 |
| BR1.4.5 | constraint | RobotTelemetry | RobotState created | Use backend-generated ISO-8601 timestamp |

**Five business rules** govern U2 telemetry: BR1.4.1 normalizes raw BLE telemetry into RobotState (lenient, per Q3); BR1.4.2 publishes state-change events per Contract 2; BR1.4.3 handles connection errors by stopping the robot and surfacing errors in the chat UI; BR1.4.4 receives command execution status from U1 per Contract 1; BR1.4.5 mandates backend-generated timestamps (per Q7).
